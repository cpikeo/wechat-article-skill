# 内容编辑指南（Content Engine，可选，仅在用户明确要求时执行）

这一步处理的是"文字本身写得好不好"，不是"排版好不好看"——**排版引擎默认只负责给用户已经写好的内容套版式，不会擅自改写用户的原文**。只有当用户明确说"帮我润色/优化文笔/调整节奏/检查专业性一致"这类要求时，才执行本文档里的内容编辑，执行前后都要让用户看到改动，不要静默替换原文。

## 一、句子节奏（可执行，效果明确）

长短句连续雷同确实会读起来单调（比如连续四句都是 12~15 字的短句，或者连续三句都是 40 字以上的长句），这是写作里一条站得住脚的经验规则，不需要什么"引擎"名字，直接作为改写时的检查项：

- 通读一遍待润色的段落，标出连续 3 句以上长度接近（字数差 ≤5 字）的地方。
- 改写时**有意让长短句交替**：一个长句给信息量，接一个短句给停顿感，不要让每句话都用同样的语法结构收尾。
- 只在用户要求"润色/优化节奏"时主动做这件事；如果用户只要排版，不要顺手把人家的句子改了。

**段落密度（和上面的"句子节奏"是两个层级，不要混为一谈）**：句子节奏管的是单句长短交替，段落密度管的是"一段该在哪里断"。外部资料给的经验数字——每段 40~80 字、手机每屏大致容纳 2~3 段——和本库已有的「段落呼吸感」规则（`editorial-identity.md` 第二节：单句 40~70 字，超过在语义断点拆句）方向一致但颗粒度不同：那条管的是句子内部会不会读起来喘不过气，这条管的是连续多段纯文字会不会变成"文字墙的文字墙"（单段不长，但十段连续堆在一起同样疲劳）。**采纳为润色时的检查项**：连续纯文字段落超过 3~4 段且中间没有任何引用/图片/列表打断时，建议在语义合适的位置插入组件打断，或者提醒用户"这段内容适合配一张图/一个要点列表"——这条是建议，不强制拆分内容本身，因为打断节奏的手段（图片/引用/列表）需要主题库真实有对应内容支撑，不能为了打断而编内容。

## 二、语气/节奏原型（用风格标签，不模仿具体真人）

**不做的事**：不会以"写成余华的风格""模仿罗振宇的语气"这类方式模仿在世的具体真人作者——这类要求即使被提出也应该婉拒，改成用下面这种通用风格标签描述"想要的语气质感"，避免生成内容被当成对某个真实公众人物的风格冒用。

可以用的风格原型（描述"质感"，不对应任何具体个人）：

| 风格标签 | 语感描述 |
|---|---|
| 极简克制 | 短句为主，去形容词，只留事实和判断 |
| 文学温润 | 意象化描写，感官细节多，节奏舒缓 |
| 杂志国际感 | 理性克制，专业术语准确，长句居多但逻辑清晰 |
| 慢生活自然 | 具体的生活场景切入，语气亲近，少说教 |
| 深度报道理性 | 数据/引语支撑观点，段落有明确的论证结构 |

用户想要某种质感时，对照这张表确认标签，而不是直接照抄某个真人的名字去"模仿"。

## 三、术语/单位/日期一致性（可执行，已配脚本）

这条是这次新增里最值得做的一条——同一篇文章里术语/单位/日期格式不统一，是真实存在、容易被忽略、又确实会让内容显得不专业的问题。已经写了检测脚本：

```bash
python3 <SKILL_ROOT>/scripts/content_consistency_check.py <文章.md 或 .html>
```

检测项：
- 同一概念的中英文/全称简称混用（比如"AI"和"人工智能"交替出现、"公众号"和"official account"混用）。
- 日期格式不统一（"2026年7月17日" 和 "2026-07-17" 同时出现）。
- 数字全角半角混用（"３个方法" 和 "3个方法"）。
- 常见计量单位书写不统一（"km" 和 "公里"、"%" 和 "百分之"）。

脚本只做**检测和列出位置**，不自动改——用哪种写法由用户的行文习惯决定，脚本没有权限替用户做这个选择，改不改、改成哪种交给用户或让 Claude 询问后再改。

## 四、结构诊断（诚实版本，不是"预测"）

判断一篇文章"开头是否抓人、有没有转折、结尾是否有力"，这是**语言理解层面的定性判断**，Claude 作为语言模型可以给出——但要如实说明这是一次主观阅读判断，不是量化预测：

- 通读全文后可以说"开头引言比较平，前三段都在铺垫背景，建议把第二段的案例提到开头"——这是具体、可核查的建议。
- **不会说**"预测 62% 的读者会在第三屏跳出"这类话——没有这篇文章、这个账号、这批真实读者的实际阅读行为数据，任何具体数字都是编出来的，不诚实。真正想知道用户在哪里流失，只有公众号后台的图文分析数据能告诉你，本 Skill 拿不到、也不会假装能拿到。

**三拍节奏检查（定性版本，不是"情绪曲线"量化评分）**：外部资料建议给文章画一条"情绪曲线"（像电影一样有起伏），这个说法本身不能落地——没有任何可靠方法能把"情绪"量化成一条曲线或一组分数，量化的部分只会是编出来的。但这个建议指向的问题是真实的，可以用定性方式检查：通读全文后回答三个问题——(1) **开场**：前 1~2 段有没有给出一个具体的钩子（案例/反常识判断/明确的读者利益），还是只在泛泛介绍背景？(2) **转折**：文章中段有没有至少一次视角/论点上的转折或递进，还是从头到尾都在同一个平面上罗列？(3) **收束**：结尾是回到开场的钩子形成闭环，还是突然结束/生硬转向 CTA？三个问题都是"能不能举出文中具体位置"的可核查判断，不是打分——回答不出具体位置，就说明这一拍缺失，可以具体建议怎么补，而不是喊"节奏感不够"这种空泛评语。

## 五、语义化设计变量命名（文档层面，不改实际渲染）

如果觉得 `Primary`/`Secondary`/`Accent` 这种命名太"UI 化"，可以在主题设计变量表旁边加一层语义别名，帮助按"这个颜色用来做什么"去使用，而不是"这是第几个颜色"：

| UI 命名 | 语义别名 | 用途 |
|---|---|---|
| Primary | Reading Anchor（阅读锚点） | 结构色/高频标记（下划线、编号） |
| Accent | Insight（洞见强调） | 稀缺锚点，全篇 ≤3~5 处 |
| Border | Whisper（安静边界） | 分割线、卡片边框 |
| Background（page） | Paper（纸感底色） | 引用块/卡片底色 |
| Muted | Caption（说明文字） | 次要说明、署名 |

**这只是命名习惯，不生成新的 CSS，也不改任何一个 hex 值**——真正的颜色定义仍然以各主题 `references/theme-{标识}.md` 里的设计变量速查表为准，语义名只是帮助理解"这个颜色是干什么用的"，登记新主题时可以选择性附上这张对照表，不强制。
