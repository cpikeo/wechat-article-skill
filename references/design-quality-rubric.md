# 专业设计质检清单

`scripts/validate_gzh_html.py` 保证的是"平台不会吃掉这段 HTML"；本清单加上 `scripts/design_quality_check.py` 保证的是"这段 HTML 排出来有专业设计师水准"。两者是正交的两道关卡，**装配完成后必须都跑**，缺一不可——合规不等于好看，好看也不能绕开合规。

判断"专业水准"不是玄学，而是可以拆成几条可核查的硬指标 + 一条无法自动化、必须人工过一遍的软指标。

## 一、可自动检测的硬指标（跑 `design_quality_check.py`）

```bash
# --accent 按本次实际使用的主题取值，见 references/theme-index.md「锚点强调色核查方式」：
# 静纸 '#6A7567' / 暖信笺 '#B8583A'——两套主题的锚点色都已和各自的结构色刻意分开，检测始终可靠。
python3 <SKILL_ROOT>/scripts/design_quality_check.py <生成的.html> \
  --accent '#6A7567' --accent-quota 4
```

- **强调色配额**：两套主题的设计变量表都写明锚点层"全篇 ≤4 处"，这是专业排版"锚点层稀缺才有效"的硬约束——静纸的锚点色（鼠尾草绿 `#6A7567`）和暖信笺的锚点色（赤陶橙 `#B8583A`）都和各自的结构色（列表圆点/竖线等用中性/暖灰）刻意分开，数 hex 出现次数是可靠信号，`--accent` 检测在两套主题上都始终适用。
- **字号阶梯**：专业排版的字号体系通常只有 4~6 级（如 12/13/15/18/22px），不是"看着差不多就再开一个新字号"。脚本统计正文里出现的不同 `font-size` 种类，超过阈值说明层级设计失控，要归并回主题设计变量表规定的几档。
- **连续重复区块**：连续 3 个及以上组件用完全相同的 `style` 字符串，视觉上会显得单调、缺少呼吸感的变化——这是新手排版最常见的"复制粘贴同一个卡片凑字数"问题，脚本会标出重复的样式串定位到具体位置。
- **无标点文字墙**：单个文本节点超过约 220 字且中间没有任何标点断句，在手机竖屏阅读时会形成压迫感极强的大段文字。专业移动端排版讲究"短句多断行"，脚本按长度+断句符号双重条件检出。
- **占位符残留**：`{{作者名}}`、`{{金句前段}}` 这类模板占位符如果原样出现在交付物里，是最低级的"没做完"信号，脚本按 ERROR 级别拦截。
- **图片过密**：相邻两张图片之间的正文字数低于阈值（默认 12 字），说明连续图片间没有文字承接，读者感觉在连续刷图而不是读文章。这条只测"字数"这个可复现信号，不判断图片本身好不好看。

五项 WARNING（含图片过密）不是"必须清零"的机械指标，而是**提示去复核**——比如强调色恰好第 4 次用在一个真正值得强调的转折句上，可以保留并说明理由；但如果说不出理由，就该删。占位符 ERROR 则必须清零。

## 二、无法自动化、必须人工过一遍的软指标

跑完脚本、清完 ERROR 之后，**用"从头到尾读一遍成品 HTML 源码 + 想象在手机屏幕上滚动阅读"的方式**过一遍下面几条：

1. **视觉呼吸感**：相邻两个"高密度"组件（卡片/表格/多图）之间是否留了足够的纯文字段落缓冲？不要让读者连续翻过三个卡片喘不过气。
2. **首屏抓人**：文章开头（标题+引言卡）在手机首屏能不能看出这篇文章值得读下去？如果开头引言卡的金句只是在复述标题，说明没做到"两层视角错开"（详见各主题库"文案策略"一节），要重写。
3. **图文比例合理**：纯文字长文（>1500 字）中间完全没有任何图片/GIF/信息图/引用块打断，读起来会疲劳；反过来，图片/组件多到盖过文字内容主体，也会显得"花而不实"。
4. **强调是否用在真正重要的地方，且没有超量**：静纸主题的锚点用量可以直接靠脚本 `--accent` 检测（≤4 处），不需要人工数；人工复核的重点是确认这几处 accent 都落在"核心结论/关键数据/全文最想让读者记住的一句话"上，而不是随手强调了一个不重要的形容词——脚本能数数量，数不出"用得对不对"。
5. **配方是否服务内容，而不是内容迁就配方**：主题库的"文章类型→组件组合配方"是常见搭配的默认值，如果这篇文章的实际内容撑不满某个推荐组件（比如没有 3 个并列要点却硬凑了三列卡片），应该减配而不是编内容凑数。
6. **结尾收束是否克制**：签名区/CTA 只出现一次，语气是否和全文调性一致，而不是突兀地切换成营销号话术。
7. **响应式细节**：图片是否都是 `max-width:100%;height:auto` 自适应，而不是固定像素宽度导致在窄屏挤压变形；长表格在窄屏是否会溢出（必要时用主题库的卡片化表格组件替代原生 `<table>`）；**任意整块内容容器**（不止图片/表格）是否被写死了较大的固定像素宽度（如 `width:560px`）而不是 `max-width:100%` 或百分比宽度——这类写法常见于把桌面端参考图/设计稿直接照搬过来的场景，手机端会横向溢出，`validate_gzh_html.py` 对此有一条 WARNING 兜底检测，但装配阶段就该按这条自查，不要等校验报错才返工。
8. **段落呼吸感节奏**：单句/单段是否大致落在 40~70 个汉字这个"读起来不累"的区间（这是软性目标，不是硬指标，`design_quality_check.py` 的文字墙检测阈值是 220 字，两者不冲突）；大号标题是否按语义断行而不是按字数硬切；引用是否用了居中排布的组件而不是左对齐大段引用。详见 [editorial-identity.md](editorial-identity.md) 第二节。
9. **图标/图片来源合规**：正文里的"图标"是否都是 emoji 或 CSS 绘制的几何图形（不是 SVG、不是图标库 CDN 链接）；图片 `<img>` 是否都指向本地文件或已知会被替换成微信域名，没有裸露的图库/图标 CDN 外链——这两条 `validate_gzh_html.py` 会自动拦截，但装配阶段就该按 [visual-assets-guide.md](visual-assets-guide.md) 的规则来，不要等校验报错才返工。
10. **标题堆叠**：连续两个及以上标题级组件（`##`/`###` 对应的标题块）中间没有任何正文/图片/引用，只是标题接标题——这条无法可靠自动检测（需要区分"标题组件"和"强调正文"，不同主题的标题样式不统一，硬编码判断规则容易和 3a/3e 强调块之类误判），人工过一遍原文结构即可发现，发现了就在中间补一句过渡正文或合并两级标题。

## 三、执行时机

放在 SKILL.md 工作流「第 5 步：校验合规」之后、交付之前，作为独立的「第 5.5 步：设计质检」执行，顺序是：

1. `validate_gzh_html.py` → ERROR 清零（否则粘贴后直接花掉，比不好看更严重）。
2. `design_quality_check.py --accent <主色> --accent-quota <配额>` → ERROR 清零，WARNING 逐条复核取舍。
3. 人工过一遍上面的软指标清单，尤其是"首屏抓人"和"强调是否用在真正重要的地方"——这两条最容易被忽略也最影响观感。
4. 三步都过了才进入「第 6 步：输出」。

## 四、常见误区

- **把"合规"当成"好看"**：0 ERROR 只是能正常粘贴，不代表排版有设计感，两道检查必须都做。
- **为了清 WARNING 而机械删减**：强调色第 4 次如果确实用在最关键的句子上，保留并说明理由比硬删更专业；design_quality_check.py 的 WARNING 是提醒去思考，不是必须服从的红线。
- **只看脚本不通读全文**：脚本抓不出"文案是否呼应主题""强调是否用对地方"这类语义问题，人工通读这一步不能省。

## 五、关于"AI 自动打综合评分"的说明

外部资料建议每次生成后由 AI 自评一个综合分数（如"Editorial Score 97/Typography 99/..."），未达标自动重来直到 95+ 才交付。这个方向（自动迭代直到达标）是对的，但**综合评分本身不采用**——本 Skill 没有真实的审美评估模型，任何"97 分"这类具体数字都是编出来的，写上去只会制造虚假的精确感，之前已经在 `content-editing-guide.md` 讨论"结构诊断"时用同样的理由拒绝过伪造阅读行为数据，这里是同一个原则。

**实际做法**：本文件第一节的硬指标（脚本可查）+ 第二节的软指标（人工核对）加在一起就是评估依据，结果是"ERROR 是否清零 + WARNING 逐条有没有说得出取舍理由 + 软指标清单逐条过了没有"，不是一个单一分数。如果要的是"生成→验证→按严重度修复→直到达标"这种更完整的闭环流程（而不只是本文件描述的一次性检查清单），可以叠加通用的 `design-qa-loop` 技能，把本文件的两道检查脚本 + 软指标清单当作它的「Acceptance Contract」证据来源，不需要在本 Skill 内部另造一套打分机制。

## 六、关于"生产稳定性"和"发布模拟器"的说明

外部资料另有一版建议提出两个诉求：(1) 同一账号多次生成质量不该忽好忽坏（"生产稳定性"）；(2) 输出前应该有一层"发布模拟器"预演公众号最终显示效果再自动修正。这两条方向都对，但需要说清楚本 Skill 实际能做到什么程度：

- **生产稳定性**：本 Skill 能提供的确定性来自"配方表驱动"而不是"每次自由发挥"——同一文章类型 + 同一主题，装配环节应该拉取配方表里规定的同一套组件搭配，而不是每次临场重新设计一套。这个纪律本身就是对抗"今天好明天差"的主要手段（自由发挥的余地越大，波动就越大），已经写在 SKILL.md 的装配步骤里；本次没有新增额外机制，因为能做的事就是"老实按配方表来"，没有更多空间。真正的模型输出随机性（同一 prompt 两次生成用词不完全一样）不是这个 Skill 的文件能消除的，属于模型本身的特性。
- **发布模拟器**：不存在能在本地精确复现微信客户端渲染引擎的方式，"模拟微信最终显示效果"做不到逐像素预演；能做到的是第二节里那几条软指标人工过一遍 + `assets/preview-template.html` 生成的移动端宽度预览页（真实还原字号/行高/配色，但不是微信客户端本身）。这就是本 Skill 版本的"发布模拟"，比对着源码 HTML 读要接近发布效果得多，但如果需要逐像素级别的保真度确认，最终还是要真的粘贴到公众号草稿箱看一眼——没有任何本地工具能替代这一步。
